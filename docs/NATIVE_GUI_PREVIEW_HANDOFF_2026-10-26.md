# J2534Diag native CAN Listener GUI preview — October 26, 2026

**Owner** `bmcleid/J2534Diag-Independent`, branch `feature/native-gui-capture-preview` stacked on PR #28. Target use: owner's TOPDON RLink X3 with a 2012 Cadillac SRX Performance AWD 3.6L, no programming or diagnostic requests.

## User workflow (Windows GUI)
1. Vehicle tab: select the **actual registered J2534 driver** from installed J2534 devices (do not guess a TOPDON DLL path).
2. Receiver: choose **Direct native CAN receiver (experimental, capture-only)**. This forces 11-bit/500 kbps and disables active diagnostic selection. The default remains **Original J2534-Sharp receiver**.
3. Click Connect. The app first checks the registered file actually exists, reads its Windows PE header to require **x64 AMD64** (not 32-bit), computes SHA-256, shows driver metadata/path/digest to the operator, and requests explicit consent. **This does not prove publisher authenticity or identify the exact DLL on this operator PC from GitHub.** If DLL is wrong, do NOT proceed.
4. In native mode Connect means *prepared*; no native `PassThruOpen/Connect/StartFilter` occurs until CAN Listener Start. Optional Disk log filename selected first and existing writer started. Start hashes and checks the same driver file again, then opens one sole-owned native device, one 11-bit CAN 500000 channel, installs 4-byte wildcard PASS_FILTER, and starts reading immediately. Uses source status+actual native `pNumMsgs` contract via `NativeCanReadBoundary`. Native read batch=100 and timeout=250ms versus original managed=200/5ms; switching after Connect is explicitly refused until Disconnect.
5. Existing CAN Listener remains the **only** in-app receiver/CSV writer/UI/filter pipeline. Disk log uses CreateNew, bounded queue and original integrity sidecar, now with `CaptureReceiver`, `NativeDriverSHA256`, and read parameters. In-memory preview retains 10,000 cap; disk recording is not subject to that cap. No new frame meanings or module identity are inferred.
6. Stop first cancels and joins reader, flushes disk writer, then stops native filter, disconnects and closes J2534 driver; only then releases existing receive lease. If cleanup fails, capture remains reserved and Stop may be retried. Disconnect disarms the selected DLL only after safe cleanup. Original managed mode retains previous behavior.

## Important limitations
**Not physically TOPDON-verified:** GitHub CI has no access to the owner's Windows installation. Actual selected path, version, cryptographic digest, signing, bitness and J2534 native compatibility cannot be certified on GitHub. Local preflight checks file existence/PE machine/SHA256; operator must compare observed publisher to their actual installed TOPDON driver. Real driver may not implement exact native interop semantics or can continue to overflow. Receive-only mode may still electrically ACK frames; no `PassThruWriteMsgs`, PID query, DTC clear, active transmission or programming added. Never call a complete disk log lossless vehicle-bus capture. Do not use while GM Techline/SPS programming is active or another J2534 process owns adapter.
